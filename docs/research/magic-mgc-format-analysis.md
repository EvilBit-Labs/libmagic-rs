# Analysis: Reverse Engineering the Compiled magic.mgc Format

> **Research Date**: January 2026 **Author**: libmagic-rs Development Team **Status**: Research Complete

## Executive Summary

This document analyzes the feasibility of reverse engineering the compiled `magic.mgc` binary format used by libmagic. Our research examined the original libmagic source code, existing reimplementations (PolyFile, arcana), and community experiences with the format.

**Key Finding**: All successful independent reimplementations of libmagic parse the **text-format** magic files, not the compiled `.mgc` binary. This approach is recommended for libmagic-rs.

## Background

The `file` command identifies file types using a database of "magic patterns." This database exists in two forms:

| Format       | Location                         | Description                      |
| ------------ | -------------------------------- | -------------------------------- |
| **Text**     | `/usr/share/file/magic/Magdir/*` | Human-readable DSL files         |
| **Compiled** | `/usr/share/file/magic.mgc`      | Binary format for faster loading |

The compiled format is generated by `file -C` or `magic_compile()` and is what libmagic loads at runtime for performance.

---

## The magic.mgc Binary Format

### Header Structure

From the libmagic source code (`file.h`), the compiled format has the following structure:

```c
#define MAGICNO     0xF11E041C  // 4-byte magic number identifier
#define VERSIONNO   20          // Current format version (changes frequently!)
#define FILE_MAGICSIZE  432     // Size of each magic entry in bytes
```

The file begins with:

1. 4-byte magic number (`0xF11E041C`)
2. 4-byte version number
3. `MAGIC_SET` (2) count fields for ASCII and binary test sets
4. Array of `struct magic` entries in **native byte order**

### Entry Structure

Each magic entry (`struct magic`) is approximately 432 bytes containing:

| Field       | Size       | Description                                  |
| ----------- | ---------- | -------------------------------------------- |
| `flag`      | 2 bytes    | Control bits (INDIR, OFFADD, UNSIGNED, etc.) |
| `type`      | 1 byte     | Comparison type (60+ types supported)        |
| `offset`    | 4 bytes    | Test position in target file                 |
| `in_offset` | 4 bytes    | Indirect offset data                         |
| `mask`      | 8 bytes    | Value mask for comparisons                   |
| `value`     | 64 bytes   | Test value (numeric or string)               |
| `desc`      | 64 bytes   | Human-readable description                   |
| `mimetype`  | 80 bytes   | MIME type string                             |
| Extensions  | ~200 bytes | Apple type, file extensions, etc.            |

### Supported Types

The format supports 60+ comparison types including:

- Basic: `FILE_BYTE`, `FILE_SHORT`, `FILE_LONG`, `FILE_QUAD`
- Strings: `FILE_STRING`, `FILE_PSTRING`, `FILE_BESTRING16`
- Dates: `FILE_DATE`, `FILE_LDATE`, `FILE_QDATE`
- Special: `FILE_REGEX`, `FILE_SEARCH`, `FILE_INDIRECT`
- Modern: `FILE_GUID`, `FILE_DER`, `FILE_OCTAL`

### Implementation Complexity

The parsing implementation resides in `apprentice.c` in the libmagic source:

- **Size**: ~3,000 lines of C code (~70KB)
- **Key functions**:
  - `check_buffer()` - reads compiled format
  - `apprentice_compile()` - writes compiled format
- **Complexity**: Handles endianness conversion, version migration, memory mapping

## How the libmagic Compiler Works

The libmagic compiler (`file -C` or `magic_compile()`) transforms text magic files into the binary `.mgc` format. Understanding this process illuminates why the binary format is tightly coupled to specific libmagic versions.

### Compilation Pipeline

The compilation occurs in `apprentice.c` through the `apprentice_compile()` function:

```c
file_private int
apprentice_compile(struct magic_set *ms, struct magic_map *map, const char *fn)
```

#### Step 1: Parse Text Files

The compiler first parses all text magic files from the Magdir directory, building an in-memory representation using `struct magic` entries.

#### Step 2: Write Header

```c
// Header structure written to .mgc file
struct {
    uint32_t magic;      // MAGICNO (0xF11E041C)
    uint32_t version;    // VERSIONNO (currently 20)
    uint32_t nmagic[MAGIC_SETS];  // Entry counts per set
} header;
```

#### Step 3: Serialize Entries

The compiler iterates through each magic set and writes raw `struct magic` entries:

```c
for (i = 0; i < MAGIC_SETS; i++) {
    len = m * map->nmagic[i];
    if (write(fd, map->magic[i], len) != (ssize_t)len) {
        file_error(ms, errno, "error writing `%s'", dbname);
    }
}
```

### Why This Creates Version Lock-in

The compiled format is essentially a **memory dump** of C structures:

1. **Native byte order**: No endianness markers or conversion
2. **Native alignment**: Struct padding depends on compiler/platform
3. **Direct struct serialization**: Changes to `struct magic` break compatibility

When libmagic developers add new fields, change field sizes, or reorganize the structure, the version number increments and older `.mgc` files become incompatible.

### The `magic_load()` Validation

When loading a `.mgc` file, libmagic validates compatibility:

```c
// From check_buffer() in apprentice.c
if (m->h.magic != MAGICNO) {
    file_error(ms, 0, "invalid magic number");
    return NULL;
}
if (m->h.version != VERSIONNO) {
    file_error(ms, 0, "version mismatch (%d != %d)",
               m->h.version, VERSIONNO);
    return NULL;
}
```

This strict version check is why you see errors like:

```text
File 5.45 supports only version 18 magic files. magic.mgc is version 16
```

**Repository**: <https://github.com/trailofbits/polyfile>

PolyFile is a "pure Python cleanroom implementation of libmagic" developed by Trail of Bits for polyglot file detection.

**Approach**: Parses **text-format** magic files only

```python
# From PolyFile source - explicitly excludes compiled format

```

**Key characteristics**:

- Supports all 263 MIME types that libmagic identifies
- Passes all official libmagic unit tests
- Discovered multiple undocumented DSL features
- Active development with 365+ GitHub stars

**Undocumented features discovered**:

1. Nested parentheses in offsets: `(&0x10.l+(-4))`
2. Hex constant suffixes: numbers ending in `h`
3. Undocumented regex flags: `/b` modifier
4. Ternary operator syntax: `${x?true:false}`
5. Search type variants: `search/b64` vs `search/b/64`

From the Trail of Bits blog:

> "In developing our independent implementation of libmagic—to the point where it can parse the file command's entire collection of magic definitions and pass all of the official unit tests—we discovered many undocumented DSL features and apparent upstream bugs."

### arcana (jhawthorn) - Ruby

**Repository**: <https://github.com/jhawthorn/arcana>

A pure Ruby implementation attempting to replicate libmagic functionality.

**Approach**: Parses **text-format** magic files only

**Key characteristics**:

- Runtime interpretation of text-based rules
- No compilation step
- Experimental status with known limitations

**Current limitations** (from README):

- "Not yet production ready"
- "Somewhat works, but has missed implementing quite a few rules"
- "Not yet safe to be run against arbitrary user input (can be made to infinite loop)"

### FFI Bindings (Not Independent Implementations)

Several libraries wrap the native libmagic C library rather than reimplementing it:

| Library        | Language | Type                    |
| -------------- | -------- | ----------------------- |
| python-magic   | Python   | FFI binding to libmagic |
| ruby-filemagic | Ruby     | FFI binding to libmagic |
| filemagic      | Python   | ctypes wrapper          |

These still depend on the system's libmagic and face version compatibility issues.

## OpenBSD's Independent Implementation

OpenBSD provides a particularly interesting case study: they wrote their own `file` command from scratch while still using the same text magic file format.

### Why OpenBSD Rewrote `file`

From the official file command homepage (darwinsys.com):

> "The OpenBSD project wrote their own implementation because they found Christos' version of my implementation to have grown too big and complex; they still use our Magic Files."

This confirms that:

1. The **text magic format is the stable interface** — OpenBSD uses the same Magdir files
2. The **implementation is separable** from the format
3. A **simpler implementation** is possible without the full libmagic complexity

### OpenBSD's Architecture

OpenBSD's implementation lives in `/usr/src/usr.bin/file/` with these key files:

| File           | Purpose                      |
| -------------- | ---------------------------- |
| `magic-load.c` | Text magic file parser       |
| `magic-test.c` | Rule evaluation engine       |
| `magic-dump.c` | Debug output of parsed rules |
| `magic.h`      | Data structures              |
| `file.c`       | Main command implementation  |

### Key Design Differences

#### 1. Runtime Text Parsing (No Compilation)

OpenBSD parses magic files at runtime using `getline()`, with no pre-compilation step:

```c
// From magic-load.c - reads text files directly
while ((line = getline(&buf, &bufsize, f)) != -1) {
    // Parse each magic rule line
}
```

#### 2. Red-Black Tree Organization

Instead of linear arrays, OpenBSD uses RB-trees for efficient rule lookup:

```c
struct magic {
    char              *path;
    RB_HEAD(...)       tree;        // Standard rules by strength
    RB_HEAD(...)       named_tree;  // Named rules for "use" references
};
```

#### 3. Cleaner Data Structures

OpenBSD's `struct magic_line` has explicit field separation:

```c
struct magic_line {
    // Offset handling
    int               indirect_type;
    int               indirect_operator;
    int64_t           indirect_operand;

    // Type and test
    int               type;
    int               type_operator;
    int               test_operator;

    // Values (union for different types)
    union {
        int64_t       number;
        double        dbl;
        char         *string;
    } value;

    // Hierarchy
    struct magic_line *parent;
    TAILQ_HEAD(...)    children;

    // Output
    char              *result;
    char              *mimetype;
};
```

### Performance Trade-off

OpenBSD chose **simplicity over startup speed**:

| Aspect      | libmagic                       | OpenBSD             |
| ----------- | ------------------------------ | ------------------- |
| Startup     | Fast (mmap binary)             | Slower (parse text) |
| Memory      | Large structs (432 bytes each) | Smaller, dynamic    |
| Complexity  | ~3000 lines in apprentice.c    | ~1500 lines total   |
| Maintenance | Version-coupled binary format  | No binary format    |

### Implications for libmagic-rs

OpenBSD's successful reimplementation demonstrates:

1. **Text parsing is sufficient** for a production-quality implementation
2. **Simpler code is achievable** without the binary format complexity
3. **The magic file format is the standard**, not the `.mgc` binary
4. **Performance can be addressed** through data structure choices (RB-trees) rather than binary compilation

## Version Compatibility Issues

The compiled `.mgc` format version changes frequently between libmagic releases, causing widespread compatibility problems:

### Documented Version Errors

From community reports:

```text
File 5.41 supports only version 16 magic files. magic.mgc is version 14
File 5.19 supports only version 12 magic files. magic.mgc is version 8
File 5.38 supports only version 14 magic files. magic.mgc is version 16
File 5.45 supports only version 18 magic files.
```

### Version History (Partial)

| libmagic Version | Format Version |
| ---------------- | -------------- |
| ~5.04            | 8              |
| ~5.19            | 12             |
| ~5.38            | 14             |
| ~5.41            | 16             |
| ~5.45            | 18             |
| Current          | 20             |

### Root Cause

From Stack Overflow discussion:

> "If you want to use them directly you need to understand the binary format (which changes over time) and load it in your own data structures. [...] The code that parses the file is in apprentice.c."

The format is:

1. **Not formally specified** - implementation is the specification
2. **Platform-specific** - uses native byte order and struct alignment
3. **Version-coupled** - tied to specific libmagic releases

## Recommendations

### Primary Recommendation: Continue with Text DSL Parsing

libmagic-rs should continue parsing text-format magic files. This aligns with:

1. **Industry precedent**: All successful reimplementations (PolyFile, arcana, OpenBSD) parse text
2. **Version stability**: Text format is stable across releases
3. **Portability**: No endianness or alignment concerns
4. **Debuggability**: Human-readable source for troubleshooting
5. **Source availability**: Text magic files ship with every Unix-like system
6. **OpenBSD validation**: A major BSD distribution proves text parsing is production-viable

### Why Not Parse .mgc?

| Factor                    | Assessment                               |
| ------------------------- | ---------------------------------------- |
| **Implementation effort** | High (~3,000 lines of complex C to port) |
| **Maintenance burden**    | High (must track version changes)        |
| **Portability**           | Poor (platform-specific byte order)      |
| **Debugging**             | Difficult (binary format)                |
| **Benefit**               | Marginal (faster startup only)           |

### Future Enhancement: Custom Compiled Format

If startup performance becomes critical, consider:

```text
Text Parser → AST → libmagic-rs compiled format (version-stable)
```

Benefits:

- Control over format stability
- Optimized for Rust data structures
- No dependency on libmagic versions
- Can include pre-compiled regex patterns

This approach provides fast loading without the maintenance burden of tracking libmagic's binary format changes.

## Appendix: Text Format Quick Reference

The text magic format (documented in `man 5 magic`) uses this structure:

```text
offset    type      test      message
```

Example rules:

```magic
# ELF executable detection
0         string    \x7fELF   ELF
>4        byte      1         32-bit
>4        byte      2         64-bit
>5        byte      1         LSB
>5        byte      2         MSB

# PNG image detection
0         string    \x89PNG\r\n\x1a\n   PNG image data
>16       belong    x                   , %d x
>20       belong    x                   %d
```

This format is:

- Human-readable and editable
- Well-documented in man pages
- Stable across libmagic versions
- The recommended input format for libmagic-rs
